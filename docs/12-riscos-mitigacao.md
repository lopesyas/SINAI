# 12. Riscos Técnicos e de Produto — Mitigação

| Risco | Impacto | Mitigação |
|-------|---------|-----------|
| Precisão do Web Speech API insuficiente em ambiente hospitalar (ruído, sotaque, jargão médico) | Médico precisa corrigir o texto com frequência, gerando fricção | Texto transcrito só é enviado após confirmação visual do médico (US-02); se a precisão for baixa no piloto, evoluir para Whisper API na Fase 2 |
| Simplificação de texto alterar o sentido clínico da pergunta | Risco clínico grave (a pergunta errada chega ao paciente) | Simplificador é baseado em regras/dicionário curado e revisado pelo responsável clínico, nunca um LLM generativo aberto no MVP; médico vê o texto simplificado antes/junto do envio |
| Qualidade/limitação da tradução do VLibras para vocabulário clínico específico | Paciente pode não entender termos médicos traduzidos literalmente | Camada de simplificação clínica atua exatamente para reduzir esse problema, traduzindo para linguagem cotidiana antes de enviar ao VLibras |
| Biblioteca visual de sintomas não cobrir o caso do paciente | Paciente não consegue responder o que realmente sente | Incluir categoria "Outro" com opção de campo livre (Could no backlog) e usar o piloto para expandir a biblioteca com os casos reais encontrados |
| Latência de rede afetando a sincronia em tempo real | Comunicação trava justamente no momento crítico do atendimento | Socket.IO com reconexão automática; histórico sempre recuperável via REST (`GET /atendimentos/:id/mensagens`) em caso de reload |
| Dependência de serviço externo (VLibras) indisponível | Comunicação médico→paciente para completamente | Fallback visível ("tradução indisponível, tente novamente" + opção de reenvio); nunca falhar silenciosamente |
| Resistência de adoção por profissionais de saúde (tempo extra por atendimento) | Baixo uso real, mesmo com produto funcionando | Piloto com etapa de simulação (Etapa A) para medir e reduzir o tempo antes de qualquer exposição real; medir tempo de comunicação como métrica central |
| Questões éticas/regulatórias (CEP, consentimento, LGPD para dados de saúde) atrasando o piloto | Cronograma de validação comprometido | Tratar aprovação ética como pré-requisito do cronograma, não como etapa paralela — iniciar essa conversa com o hospital já na Fase 1, em paralelo ao desenvolvimento técnico |
| Equipe pequena não conseguir sustentar as integrações externas + interfaces no prazo de 30 dias | MVP atrasa ou sai incompleto | Escopo do MVP definido para depender só de soluções já existentes (VLibras, Web Speech API), evitando qualquer construção de IA própria nesta fase (ver [Stack de Tecnologias](03-stack-tecnologias.md)) |
| Reconhecimento de sinais (Fase 2) sair caro/impreciso quando implementado | Investimento em ML sem retorno claro | Escopo da Fase 2 restrito a um conjunto fechado de sinais médicos pré-treinados, não Libras livre — reduz drasticamente o risco técnico em relação a um reconhecedor genérico |
